# RT-008: Deterministic Readiness Verification

## Status

Accepted for implementation. This specification implements GitHub issue #8 on
top of RT-007 Technical Research Packages. It verifies a persisted package
snapshot; it does not change the Working Brief, Blueprint Target, or Decision
Ledger.

## Public API

```python
record = ReadinessVerifier(store).verify(
    round_id="round-001",
    readiness_id="readiness-001",
    technical_package=technical_package,
    repository_roots={"input-repository": repository_root},
    risk_tier="medium",
)

delivery_readiness = readiness_for_delivery(record)
```

`record` is an immutable `readiness-record` artifact. `delivery_readiness`
returns exactly the structured mapping accepted by `DeliveryCompiler`; the
record's diagnostics remain available for an implementation agent and a
requester without being flattened into prose.

## Gates

The verifier deterministically evaluates six gates:

1. `intent_alignment`: the package exposes the Working Brief's leading
   interpretation and material viable alternatives exactly as recorded by the
   source Intent Model.
2. `decision_closure`: every visible Decision Slot has a usable Decision
   Ledger state. A missing or blocked slot fails. Conditional decisions need a
   concrete validation oracle; deferred decisions need a fallback. Either is a
   valid closed state when that structural evidence is present.
3. `traceability`: each P0 decision retains an exact ledger/finding/input
   lineage, anchor, design consequence, task, and acceptance oracle.
4. `repository_fit`: repository-backed touchpoints are resolved against an
   explicitly supplied read-only root; greenfield work is recorded as not
   applicable rather than treated as a passing repository check. The blocking
   handoff check covers P0 touchpoints; lower-priority surfaces remain in the
   package and can be promoted by a later target revision.
5. `implementation_readiness`: every P0 selected or conditional decision has
   an actionable change task, validation, and matching ordered implementation
   plan entry; deferred work has a reversal-safe fallback.
6. `operational_quality`: recorded rollout/rollback/observability is checked
   proportionally to risk. Unknown operational behavior stays visible as
   `deferred` for default/medium risk and fails at high risk.

## Diagnostics And Follow-up

Every non-passing gate emits a structured diagnostic with its gate, status,
summary, affected Decision Slot, ledger entry, and/or Work Item where known.
Each actionable failure emits a deterministic targeted Work Item recommendation
without creating that Work Item or changing the Blueprint Target. The delivery
projection exposes its recommended ids as `next_work_item_ids`.

## Invariants

- The Technical Research Package, its Brief, Intent Model, Target, inputs,
  decisions, and findings must resolve to exact stored revisions in one round.
- Decision Records and Blueprint Closure entries are treated as derived views:
  their complete fields must match the exact Decision Ledger and Blueprint
  Target rather than merely carrying a matching id and revision.
- Repository inspection only reads files under a caller-provided root; it does
  not execute repository code and does not mutate the repository. Python
  symbol anchors are resolved through top-level AST definitions, never a text
  match in a comment or string.
- Each implementation-plan task and its rollback handoff must still match the
  exact Decision Ledger task, validation, and fallback from the package.
- The verifier does not infer hidden user intent, claim a package correct from
  prose completeness, or create a new user round.
- A failed gate is a valid readiness result, not a failed verifier invocation.
- Artifact or payload schema misuse is rejected before a readiness record is
  appended.

## Test-First Acceptance Cases

| Case | Expected result |
| --- | --- |
| missing P1/P0 closure | decision-closure fails, names the slot, and emits a targeted follow-up |
| conditional P0 decision | structural P0 chain remains traceable and implementation-ready when its validation/task are concrete |
| missing repository touchpoint | repository-fit fails with the slot and path in the diagnostic |
| multiple repositories | each touchpoint is checked against the repository baseline that observed it |
| greenfield package | repository-fit is `not_applicable`, not silently passed |
| high-risk operational unknown | operational-quality fails and recommends a targeted operations task |
| corrupted plan, rollback, or intent projection | corresponding readiness gate fails rather than trusting rendered package data |
| rehydration | readiness record retains package and exact source parent refs deterministically |
