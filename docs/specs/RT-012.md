# RT-012: Time-Split Blueprint Evaluation Suite

## Status

Accepted for implementation after RT-011. This specification evaluates whether
an exact Technical Research Package lets a separately operated implementation
runner deliver a validated change. It is not a citation-count or prose-similarity
benchmark.

## Dataset Contract

Each versioned case has two deliberately separated parts:

- public case metadata: a permitted repository locator, immutable pre-change
  baseline revision, environment recipe, and the materials available to the
  research and implementation agents; and
- evaluator-owned material: the eventual patch, review discussion, and hidden
  acceptance oracle. It is never included in the implementation request.

The repository locator must be public or explicitly licensed for evaluation.
A case records its corpus version, source licence or permission note, baseline
revision, reproducible environment digest, and an opaque hidden-oracle id. The
suite validates that these fields are present before it accepts a case; it does
not download repositories or publish hidden material.

`evaluation/cases/v1.json` is the initial two-case public manifest. Its
baseline checksum is a SHA-256 fingerprint of the canonical repository locator
and pinned revision descriptor; evaluator-owned snapshots and hidden material
are intentionally outside this repository. Each case can therefore be replayed
from the recorded public baseline while the reference change stays unavailable
to the research and implementation agents.

## Public API

```python
case = TimeSplitCase.from_mapping(case_mapping)

record = BlueprintEvaluationSuite(store).evaluate(
    round_id="round-001",
    evaluation_id="evaluation-001",
    case=case,
    technical_package=technical_package,
    readiness_record=readiness_record,
    risk_verification_record=risk_record,
    cost={"tool_calls": 42, "seconds": 810},
    clarification_burden={"asked": 2, "unanswered": 0},
    implementation_runner=independent_runner,
    baseline_result=simpler_baseline,
)
```

The runner receives only the pinned pre-change baseline and exact technical
package/readiness snapshots. The evaluator owns any hidden acceptance archive
or regression oracle. RT-012 never passes a reference patch, discussion, or
hidden test text into the runner request.

## Measurement

Every immutable `blueprint-evaluation` record includes:

- structural scores for decision closure, traceability, and repository-anchor
  accuracy, derived from exact persisted package and readiness revisions;
- independent `build`, `fail_to_pass`, and `pass_to_pass` results, with command
  names and reproducible environment information;
- risk-verification evidence when RT-011 was selected;
- cost and clarification burden;
- a named simpler baseline comparison; and
- component-level diagnoses rather than one aggregate-only score.

`fail_to_pass` means the hidden acceptance behavior required by the target.
`pass_to_pass` means pre-existing regression behavior. A case that cannot
exercise either dimension records it as `not_applicable` with a reason, never
as a passing test.

## Failure Diagnosis

The independent runner returns zero or more structured diagnoses. Each names
one product component: `intent`, `intake`, `decision_map`, `work_items`,
`decision_ledger`, `technical_package`, `readiness`, `risk_verification`, or
`implementation`. Invalid or global-only diagnoses are rejected. The resulting
record preserves the raw category, affected decision slot/work item where
known, and a concise evaluator limitation.

## Invariants

- A case baseline, corpus version, and environment digest are immutable and
  required for reproducibility.
- The implementation request contains no reference patch, discussion, hidden
  test body, or host repository root.
- The suite does not execute a repository itself; an injected independent
  runner supplies command outcomes in a controlled evaluator environment.
- Actual implementation outcomes and structural package scores remain separate.
- Evaluation records have exact package, readiness, and optional RT-011 parent
  lineage. A simpler baseline is an explicit comparator, not an inferred
  reference-plan similarity score.

## Test-First Acceptance Cases

| Case | Expected result |
| --- | --- |
| valid pinned case | corpus version, baseline, and environment are persisted and the runner receives only allowed public inputs |
| hidden eventual material | request construction rejects any patch/discussion/oracle payload field |
| implementation outcome | `fail_to_pass` and `pass_to_pass` are separately recorded with build status |
| structural failure | closure, traceability, or anchor measurements remain visible even when the implementation run fails |
| diagnosis | a failed run identifies a supported product component rather than only a global score |
| baseline comparison | a named simpler baseline result and its limitations are recorded alongside the blueprint result |
