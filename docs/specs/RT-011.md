# RT-011: Risk-Tiered Isolated Implementation-Readiness Verification

## Status

Accepted for implementation. This specification extends RT-008 deterministic
readiness verification with an execution-level verification boundary. It does
not execute repository code in the research-tree host process and does not
change a Working Brief, Blueprint Target, or Decision Ledger.

## Goal

Structural readiness checks are sufficient for ordinary work, but not for every
uncertainty. RT-011 applies a proportionate policy:

| Risk tier | Structural checks | Execution-level check |
| --- | --- | --- |
| `default` | Required | Both execution checks are explicitly skipped. |
| `medium` | Required | An optional isolated `targeted_spike` can test a bounded unknown. |
| `high` | Required | An independent `independent_implementation_run` is required before implementation readiness can pass. |

The default interface remains compatible with RT-008. A caller that does not
provide an execution adapter receives the normal structural result plus an
immutable record of which execution checks were skipped and why. High-risk
readiness cannot pass without its independent run.

## Public API

```python
record = ReadinessVerifier(store).verify(
    round_id="round-001",
    readiness_id="readiness-001",
    technical_package=technical_package,
    repository_roots={"input-repository": repository_root},
    risk_tier="high",
    verification_adapter=isolated_adapter,
)
```

`verification_adapter` implements one method:

```python
class IsolatedVerificationAdapter(Protocol):
    def run(self, request: IsolatedVerificationRequest) -> IsolatedVerificationResult: ...
```

The request contains only an immutable, sanitized repository-baseline snapshot
and an exact Technical Research Package snapshot. It intentionally contains no
live repository root, host environment, secret values, or host command runner.
The research-tree runtime never invokes shell commands or repository code for
this feature. A production adapter can provision an isolated copy; tests use
deterministic fake adapters.

## Isolated Run Contract

An execution result records:

- the requested check kind and pass/fail status;
- exact repository input refs and baseline revisions;
- exact package ref and content hash;
- declared commands and named results;
- an isolation attestation: no host secrets exposed, no source repository
  mutation, an isolated working copy, and disabled network access; and
- on failure, one normalized cause category and same-round remediation target.

High-risk successful runs must cover named `build`, `hidden_acceptance`, and
`regression` commands and results. A result that claims success but violates
the isolation attestation is downgraded to a failure. The source repository is
not passed to the adapter, so the host runtime cannot grant it mutation access.

## Failure Feedback

Execution failures must be classified as exactly one of:

- `intent`
- `repository_fit`
- `decision_evidence`
- `design_detail`
- `implementation_task`
- `oracle_quality`

Each failure identifies a current Decision Slot or Work Item. RT-011 writes a
same-round follow-up into the immutable Readiness Record, maps the category to
the affected readiness gate, and emits the usual targeted work recommendation
when a slot is known. It does not create a successor brief: a failed spike or
implementation run is internal evidence for the current target.

## Readiness Record Extension

Every `readiness-record` includes a `risk_verification` object containing the
selected policy, sanitized exact baseline, exact package ref/hash, executed
checks, skipped checks, and same-round follow-ups. `delivery_readiness` stays
unchanged so RT-007 DeliveryCompiler consumers remain compatible.

## Invariants

- No execution adapter receives a host filesystem root, environment mapping,
  secret value, or arbitrary-command callback.
- RT-011 itself does not use subprocess execution or mutate an inspected
  repository.
- A high-risk run cannot pass without all three required command/result names,
  exact package/baseline versions, and a safe isolation attestation.
- A failed execution run is a valid persisted readiness result, provided its
  category and current-round remediation target are valid.
- Schema misuse, mismatched check kinds, unrecognized failure categories, or
  malformed result evidence is rejected before a readiness record is appended.

## Test-First Acceptance Cases

| Case | Expected result |
| --- | --- |
| default risk without adapter | structural verification remains compatible and both execution checks have explicit skip reasons |
| medium isolated spike | fake adapter receives no live root or secret data and its command/result evidence is persisted |
| high successful run | exact baseline/package versions plus build, hidden-acceptance, and regression commands/results are persisted; implementation readiness passes when structural gates pass |
| high failed run | one normalized category maps to the relevant gate and creates a same-round Decision Slot/Work Item follow-up |
| unsafe adapter attestation | claimed success is rejected as a readiness failure and source mutation or secret exposure never becomes a passing result |
