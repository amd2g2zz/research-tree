# RT-010: Adaptive Work Portfolio Scheduling

## Status

Accepted for implementation. This specification implements GitHub issue #10
on top of RT-005 Work Items and RT-006 Decision Ledger provenance.

## Public API

```python
portfolio = AdaptivePortfolioScheduler(store).schedule(
    round_id="round-001",
    portfolio_id="research-portfolio",
    blueprint_target=target,
    work_items=(work_a, work_b),
    scoring_inputs={
        "work-a": {
            "expected_information_gain": 80,
            "cost": 12,
            "duplicate_risk": 5,
        },
    },
    tool_call_budget=16,
    max_parallelism=2,
    prior_portfolio=None,
    event=None,
)
```

The result is one immutable `work-portfolio` artifact. It contains a local,
rebuildable Work Item dependency DAG, factor-by-factor scores, ready ordering,
dispatch batches, per-work dispatch decisions, budget accounting, and the
event that produced this schedule revision.

## Scheduling Contract

- The input Work Items are exact, latest persisted revisions for one exact
  Blueprint Target revision. A portfolio rejects stale Work Item revisions,
  duplicate ids, unknown dependencies, dependency cycles, and duplicate
  Decision Slot work before writing an artifact.
- The dependency DAG is scoped to the supplied Work Item portfolio. It is not
  used as a provenance graph, evidence graph, or replacement Decision Map.
- A reproducible integer heuristic exposes all factors:
  `impact`, `uncertainty`, `downstream_leverage`, `irreversibility`,
  `expected_information_gain`, `cost`, and `duplicate_risk`.
- A work item is dispatchable only when it is non-terminal, all dependencies
  are complete, it is not a duplicate, and its Work Item budget fits the
  remaining portfolio budget. A batch contains only pairwise independent work
  and never exceeds `max_parallelism`.
- Every work item receives a decision (`dispatch`, `waiting`, `deferred`,
  `cancelled`, `running`, or `complete`) with an explicit reason.

## Replanning Contract

Later revisions of the same portfolio require an exact prior portfolio and a
structured event. Supported events are `evidence_conflict`,
`prototype_failure`, `repository_fact_disproved`, `new_p0_decision`,
`budget_saturated`, and `cancellation`. The new revision references the prior
portfolio first and records affected Work Items and exact supporting artifact
references. It does not create a user round.

## Test-First Acceptance Cases

| Case | Expected result |
| --- | --- |
| same input portfolio | identical DAG, scores, readiness ordering, and dispatch batch across fresh stores |
| independent ready work | only unrelated ready Work Items share one dispatch batch |
| dependency and budget | dependent work waits; exhausted budget yields explicit deferred decisions |
| duplicate or cycle | duplicate work is cancelled with a reason; a dependency cycle rejects before persistence |
| event-driven replan | later revision retains prior portfolio provenance and names the event that changed priority |
