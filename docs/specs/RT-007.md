# RT-007: Structured Technical Research Packages and Human Briefs

## Status

Accepted for implementation. This specification implements GitHub issue #7 on
top of RT-002 intake, RT-003 intent/brief compilation, RT-004 Blueprint
Targets, and RT-006 Decision Ledger entries.

## Public API

~~~python
deliveries = DeliveryCompiler(store).compile(
    round_id="round-001",
    technical_package_id="technical-package",
    human_brief_id="human-brief",
    working_brief=brief,
    blueprint_target=target,
    decision_entries=(decision_a, decision_b),
    readiness={...},
)
~~~

"deliveries.technical_package" and "deliveries.human_brief" are separate,
immutable artifacts. The compiler accepts only exact persisted structured
artifacts plus a structured readiness record. It does not accept worker report
text, architecture prose, or an OpenSpec request/output parameter.

## Inputs and Lineage

- The Working Brief, Intent Model, Blueprint Target, selected Input Ledger
  artifacts, and Decision Ledger entries must belong to the requested round and
  resolve to exact stored revisions.
- Every supplied Decision Ledger entry must belong to the exact Blueprint
  Target, be the latest revision of its decision id, and have a unique Decision
  Slot.
- Repository baseline data is read from the Working Brief's exact selected
  Input Ledger parents. It is never supplied as unanchored free text.
- Both outputs retain parent references to their Brief, Intent Model, Blueprint
  Target, selected input baselines, and selected Decision Ledger revisions.

## Technical Research Package Contract

The package payload must include these structured sections:

1. "round_and_scope": Working Brief scope, non-goals, retained constraints,
   assumptions, input roles, and conflicts.
2. "intent_basis": literal signals and explicit intent hypotheses with
   confidence, source inputs, and design consequences.
3. "technical_baseline": repository revision, anchors, facts, unreadable
   boundaries, or an explicit greenfield state.
4. "blueprint_closure": every Decision Slot, including a "missing" closure
   record when no current Decision Ledger entry exists.
5. "decision_records": selected option, alternatives, finding/source anchors,
   change surface, validation oracle, fallback, reversal condition, and
   implementation tasks.
6. "recommended_design": deterministic views grouped by architecture,
   interface, state, security, operations, migration, and validation slots.
7. "implementation_plan", "risks_and_validation", "readiness_record", and
   "traceability".
8. "rollout_and_observability": a typed view of only `migration` and
   `operations` Decision Slots. It is `unknown` with a next action when those
   slots or their decisions are absent; it never invents operational behavior.
9. "operational_handoff": a rollout/rollback/observability view derived from
   ordered change tasks, validation oracles, slot status, and recorded
   fallbacks. It is an implementation handoff, not free-form operational prose.

For every P0 "selected" or "conditional" decision, the compiler requires an
intent hypothesis, anchor, design consequence, repository touchpoint or
greenfield assumption, validation oracle, fallback, reversal condition, and at
least one change task with an acceptance oracle. Invalid input leaves neither
delivery artifact behind.

The delivery compiler revalidates this semantic contract even for a revision
written directly through `RunStore`: decision anchors must contain supported,
nonempty `kind` and `ref` fields; repository touchpoints must conform to the
Decision Slot (or have an explicit greenfield basis); selected options and
alternatives must remain valid slot choices; and every emitted change task must
have an id, description, acceptance oracle, and a slot-constrained touchpoint
or explicit greenfield basis. P0 selected/conditional decisions must also have
a linked, anchored Finding Pack that covers the selected option. This makes the
delivery boundary safe even when a generic storage writer bypassed the Ledger
compiler.

## Human Brief Contract

The Human Brief is separately compiled from the same structured inputs. It
contains the current understanding, recommended direction, important choices
and trade-offs, near-term result, readiness, and material risks. It references
the Technical Research Package artifact but must not contain its raw decision
ledger, source table, or implementation task dump.

It also contains a concise, standalone list of every missing, conditional,
deferred, or blocked Blueprint Closure item, including its status, fallback,
and next action, plus the readiness findings and next work item ids. A reader
does not need to open the Technical Research Package to understand why the
direction is not fully ready.

## Readiness Input

"readiness" is a structured mapping with risk tier, the six readiness gates,
finding summaries, and next work item ids. The package shows failed, deferred,
and missing closure as explicit structured data and rendered text. It must not
imply readiness merely because a document was produced.

If any Blueprint Closure item is `missing` or `blocked`,
`readiness.gates.decision_closure` must not be `pass`; the compiler rejects
that contradictory input before appending either delivery. A `conditional`
entry with a concrete validation oracle and a `deferred` entry with an explicit
fallback remain visible, but are valid closure states for a downstream
readiness verifier to assess.

## Non-goals

- Do not generate OpenSpec artifacts by default or accept worker prose for
  output assembly.
- Do not implement source acquisition, a readiness verifier, a service/UI, or
  a new research scheduler.
- Do not mutate prior Decision Ledger, Brief, or input revisions.

## Test-First Acceptance Cases

| Case | Expected result |
| --- | --- |
| complete structured decision | both delivery artifacts contain implementation fields, exact traceability, and independent human wording |
| P0 decision missing a required field | compilation fails before either artifact is written |
| unclosed Decision Slot | technical package shows a "missing" closure record and fallback rather than hiding it |
| stale/mismatched ledger revision | compilation rejects it before writing artifacts |
| worker prose/OpenSpec input | public compiler API has no such assembly path and output contains no OpenSpec artifact |
| rehydration | both output artifacts retain exact parent refs and render deterministic markdown |
| Human Brief with an unclosed slot | its standalone document and markdown name the status, fallback, next action, readiness finding, and next work item |
| contradictory closure gate | a `pass` decision-closure gate with unclosed Blueprint Closure is rejected before outputs |
| direct storage P0 mutation | malformed anchor/touchpoint/task/option/alternative data is rejected before outputs |
| operational boundary absent | rollout or observability is explicitly `unknown` with a next action rather than inferred |
