# RT-001 方案设计

## ADR-001: Local JSON append-only run store

### Context

The product must retain immutable lineage across recursive research rounds,
while allowing future modules to write heterogeneous contract artifacts. The
repository currently has no runtime to preserve, so the first implementation
should remain inspectable and deterministic rather than introduce a service or
database before the product has stable domain behavior.

### Decision

- Use Python 3.11+ with PEP 621 packaging and a `src/` layout.
- Use the standard library for production code; use `pytest` only for tests.
- Persist versioned JSON envelopes under an explicitly supplied `RunStore`
  root. JSON is human-inspectable, portable and sufficient for local,
  deterministic tests.
- Perform structural schema validation at the persistence boundary with
  immutable dataclasses and explicit `from_dict` validators. This validates
  storage envelopes now without prematurely imposing schemas on future Intent
  Model or Decision Ledger payloads.
- Build state by replaying immutable files; do not create a global current-run
  file, singleton, cache, or environment-derived workspace.
- Expose a small application API and two CLI commands. Future product modules
  depend on protocols in `ports`, not on file paths or CLI code.

### File and write model

Each newly created file is first written and flushed in the target directory,
then linked into its final unique path. A collision raises an error rather than
overwriting stored history. Artifact revision allocation retries after a
collision, so concurrent append attempts for one artifact id can still retain
both revisions. Event ids are UUID-based and therefore do not require a shared
counter.

### Consequences

This establishes a stable, inspectable local contract with no production
dependency. It does not offer distributed transactions, database indexing,
cross-process locks for every possible failure mode, encryption, or migrations;
those capabilities require evidence from later product work. A malformed file
is detected during reload rather than silently repaired.

### Test workflow

`uv sync --group test` prepares a clean checkout from `uv.lock`; `uv run
pytest -q` is the authoritative test command. The runtime itself can also be
exercised with `python -m research_tree` after installation or through
`uv run python -m research_tree`.

## Integration direction

The following future modules receive a `RunStore` through their application
service rather than read a global workspace:

- intake writes Input Ledger and Context Bundle artifacts;
- intent writes revisable Intent Model artifacts;
- strategy writes Working Brief, Strategy and Blueprint Target artifacts;
- research writes Work Item and Finding Pack artifacts;
- convergence writes Decision Ledger artifacts;
- delivery writes the two compiled deliverables; and
- verification writes Readiness Record artifacts.

# RT-002 方案设计

## 领域边界

新增 `InputIntakeService`，它只依赖显式传入的 `RunStore`。服务将每个 input 写为
`input-ledger-entry` artifact；artifact id 即调用者提供的 stable input id。文本
材料把 inline content 与 SHA-256 revision 一起保存。repository 材料把 immutable
`RepositoryBaseline` 保存为 ledger payload 的扩展字段。该服务不修改 `RunStore`
的文件格式或 RT-001 的公共 API。

Context Bundle 同样是一个 `input-ledger-entry`，其 `kind` 为 `context_bundle`。
除了契约要求的 `member_input_ids`，payload 保存 `member_refs`，并把这些 exact refs
作为 `RunStore.append_artifact` 的 `parent_refs`。因此 bundle 既保留用户分组，也绑定
当时的成员 revision；它不复制、融合或解释成员内容。

`used_by_rounds` 在此版本记录创建它的 round。跨 round 的使用必须在将来以新的、
不可变 lineage/input-use artifact 表示，不能原地修改旧 ledger payload。

## RepositoryBaseline

baseline 的结构为：canonical repository root、只读 scope、Git branch/commit/dirty
状态（可用时）、安全扫描得到的 content fingerprint、可解析 anchors、分类 facts 和
unreadable records。facts 只描述观察到的文件和保守的语法/命名信号；例如 `main.py`
是 candidate entry point，而不是架构推荐。

扫描器使用标准库，永不调用 repository 中的可执行文件、测试、构建工具或 hook。
Git metadata 查询仅使用受限的 `git rev-parse`/`git status --porcelain` 子命令，并在
Git 不可用时明确留下空 revision 字段。Python 文件可通过 `ast` 提取顶层 symbol；
其他语言只产生 path anchor，不能伪装为完整语义分析。

## 安全策略

`RepositorySafetyPolicy` 具有可测试、显式的默认值：单文件大小、总读取预算、最大
文件数、默认忽略目录、secret 路径规则和 binary 扩展名。每个候选路径在读取前均以
canonical root 验证；repository root 自身是 symlink 时拒绝 intake，其他 symlink 都不跟随，外链 symlink 的 reason 为
`external_symlink`，内部 link 的 reason 为 `symlink_not_followed`。secret 路径在
打开前被排除，binary 只允许有限 probe，超限内容不被读取。

`include_paths` 可以把 reconnaissance 缩小到 repository 内路径。越界或不存在 scope
转化为 unreadable record，而非让整个 intake 失败；记录中的安全 scope 使用 repository-relative
路径；不存在的 repository root、非法
ledger 字段和未知 bundle 成员仍是调用错误。

## 测试策略

先以 public service API 写行为测试：文本和 bundle 的 artifact/revision/lineage、Git
baseline 的 anchors、重登记不变性，以及安全策略的每个 reason。路径边界逻辑在纯
函数级别可测试，真实 external symlink 只在平台允许时作为额外集成覆盖，从而不以
skip 取代安全规则验证。

## RT-004 方案设计

`BlueprintTargetCompiler` 是 Working Brief 与后续 research 工作之间的纯编译边界。它
不猜测架构，也不执行研究；调用者提供结构化 Decision Slot，编译器验证 slot 是否真的
足以驱动有界研究和后续收敛，并将其作为 `blueprint-target` artifact 追加到同一 round。

每次重编译同一 target id 都带 `change` 描述。首版必须为 `initial`；后续 revision 只接受
`add`、`split`、`merge`、`remove` 或 `reprioritize`，并把前一个 target revision 放入
`parent_refs`。这让 research 发现带来的地图变化可解释，而不是静默替换列表。

仓库锚点从 Working Brief 的精确 Input Ledger parent refs 中读取。带 repository baseline
的 slot 必须引用存在的 path/symbol；没有 repository 的 slot 必须使用空 touchpoint 并写出
greenfield assumption。P0 同时必须绑定 Brief 中可见的 Intent Model hypothesis，避免把
与当前目标无关的高优先级研究塞进地图。

## RT-005 方案设计

`WorkItemPlanner` 读取一个精确 Blueprint Target revision，只对 `open` / `researching`
slot 生成工作。它不会从关键词猜测研究方式：默认方法由已记录 repository touchpoint
决定（`repository_inspection` 或 `primary_docs`），而 scope、decision change reason 和
Finding Pack completion contract 都直接来自该 slot 的决策边界。

Planner 使用调用方提供的稳定 work item id 映射，先按 slot dependency 做稳定拓扑排序，
再以 `serial` 模式串联或以 `dependency_respecting` 模式保留对应的 work dependency。每个
artifact 直接引用 Target；所有 work dependency 必须引用已持久化的同 round Work Item。

`WorkItemStatusService` 不在原 artifact 上改状态。它为同一 work id 追加 revision，并把
前一 Work Item 与当前 Target 都列为 parent refs。调用方必须给出非空 reason，因而取消/延期
总能解释为目标关闭、supersession 或显式运营决定。

## RT-006 方案设计

`FindingPackCompiler` 只接收已持久化的 Work Item，并反查其 exact Blueprint Target 和
Decision Slot。它把每个 observation 锚定为 source/repository/input/experiment 事实，并校验
option effect 不会引用 slot 外的候选方案。它不在此阶段选方案。

`DecisionLedgerCompiler` 则以同一 target/slot 的 Finding Pack 为输入，追加
`decision-ledger-entry`。P0 的 `selected` / `conditional` 状态必须具备至少一个 finding
anchor、设计后果、至少一项变更任务和带 oracle 的验证；`deferred` / `blocked` 可以没有
finding，但不能没有 fallback。重算同一 decision id 时将旧 decision 放在第一个 parent ref，
所以冲突、条件选择与 reversal 可以审计而不覆写历史。
